Interpretation boundary

Integration success is not policy success.

05 / 07

Established by exp01b

  • The CaP-X trial harness reaches both simulators.
  • Repository-oracle Python executes with sandbox return code 0.
  • Both privileged APIs can complete one concrete task.
  • Task predicates and reward propagate into a common result schema.
  • Videos and per-trial artifacts are produced and replayable.

Not established by exp01b

  • No model generated the successful programs in these two rows.
  • No learned low-level control policy was evaluated.
  • No RL training, improvement curve, or credit assignment was tested.
  • One task and one trial per simulator do not measure generalization.
  • Cross-embodiment transfer remains a design target, not a result.

Correct claim: “the adapter and execution substrate work.”   Incorrect claim: “CaP-X has learned to solve RoboTwin and LIBERO.”

Success semantics

Keep three outcomes separate.

03

Task success

Did the simulator's terminal predicate confirm the physical goal? Here: 2/2.

Program evidencecode.py + all model/oracle responses
Execution evidencesummary.txt + sandbox return code + elapsed time
Behavior evidencevideo_combined.mp4 + task-completion naming

This decomposition is the useful RL interface: execution failures, planning failures, and task failures can receive different diagnostics and rewards instead of collapsing into one bit.

  1. Oracle → generated code

    Measures the isolated code-generation gap.
  2. Scale seeds and tasks

    Run 10–20 seeds across multiple LIBERO and RoboTwin tasks.

    Report execution, planning, and task-success rates separately.
  3. Add recovery and failure taxonomy

    Log which primitive failed, state before/after, retries, and regeneration count.

    Turns failures into trainable, inspectable trajectories.
  4. Train across embodiments

    Define a shared semantic action layer while retaining backend-specific executors.

    Test shared policy vs per-embodiment policy under matched budgets.

Research direction: use the verified harness as a procedural-verifier RL environment—reward program validity, planner feasibility, and physical task completion as distinct signals.
